1. Research problem

Teams often show charts without a decision. Partners need: what failed, for whom, how sure we are, and what to change next. The failure mode of “quant UXR portfolios” is a methods collage that never influences a product call.

Hypothesis for this study: a shared readout grammar (decision → KPIs → breaks → segments → method) across survey, usability, and A/B makes validation transferable — the same way a real research ops motion would.

2. Study design thinking

  • Define metrics before plots. SUS / trust / frustration each have a direction of “better.” Completion alone is treated as incomplete evidence.
  • Reduce variables in the UI. Top filter bar scoped to partner-relevant cuts (device, experience, task, country) — not every column in the CSV.
  • Decision banners carry severity. High / medium / low priority language mirrors how I’d brief design and engineering.
  • Model as diagnostic, not theater. Logistic task-success check (ROC-AUC ≈ 0.96) shows UX features separate outcomes; it is not framed as a production scorer.

3. Three validation modes (deep cuts)

Survey validation

When people finish a task, is the experience actually good — or just completable?

Measured: SUS, trust, ease, frustration, completion time · success vs fail gaps · device / experience segments

Product decision: Treat completion as necessary but not sufficient. Mid SUS with high completion → clarity and trust work before new features.

Usability testing

Which tasks create the most friction (errors, help, frustration) and should be redesigned first?

Measured: Task success, error counts, help rate, time, satisfaction · task friction ranking

Product decision: Rank redesign candidates by errors + frustration, not success rate alone.

A/B experiment

Does a conversion lift come with an acceptable experience — or higher bounce / worse load?

Measured: Conversion %, bounce %, load time, session length, device segments

Product decision: Conversion is primary; bounce and load are quality guards before calling a winner.

4. Pipeline (how the work actually runs)

raw educational CSV
  → src/clean_*.py (impute, clip, attention checks, labels)
  → data/processed/*_analysis_ready.csv
  → Streamlit pages (decision → KPI → break → segment → method)
  → Community Cloud redeploy on git push

Reproducibility mattered as much as charts: cleaners are scripts, not one-off notebook cells, so a new study type can follow the same pattern (feature adoption / funnel next).
