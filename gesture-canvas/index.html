1. Why this exists

Gesture and camera-based input look magical in demos and fail quietly in real use. I built a public probe so I can talk about discoverability, feedback, and recoverable errors with evidence you can feel — not only slides.

2. Research questions (the deep cut)

Can people discover gesture affordances without a tutorial wall?

Novel input dies when first-use friction is high. Probe onboarding length vs discovery.

What feedback states make tracking feel trustworthy vs broken?

Same problem as invisible AI: when the system fails silently, users invent wrong mental models.

Which failure modes are recoverable (retry) vs session-ending?

Maps to severity ranking you’d use in a usability readout for a hardware + software team.

3. How I’d study it formally

  • Think-aloud first-use sessions (n small, high signal) on draw / erase / mode switch.
  • Code errors: lost tracking, lag, unintended strokes, mode confusion.
  • Compare feedback prototypes (cursor ghost, confidence meter, haptic-less visual pulse).
  • Severity + confidence readout for engineering — same grammar as the Quant UX suite.

Honest status: the live build is the probe. Formal moderated n and coded themes are the next rigor step.

4. AI workflow — collaborator, not author

AI helped me ship the demo faster. Research questions, prototype honesty, and what “good” means for gesture UX stayed mine. (Portfolio AI process.)

Phase 1 · Define the research probe

I owned: Scoped GestureCanvas as a mixed-methods probe for gesture UI — not a finished productivity app. Named success as learnability + feedback clarity.

AI helped: Helped scaffold browser / MediaPipe integration paths and debug camera permission edge cases.

Phase 2 · Ship a demo people can try

I owned: Pushed for a public GitHub Pages demo so interviewers can experience the interaction, not only screenshots.

AI helped: Accelerated HTML/JS iteration and deploy friction; I owned interaction design choices and research framing.

Phase 3 · Portfolio case depth

I owned: Wrote the study as research questions + failure modes (Grace-style product depth), not a tech demo dump.

AI helped: Drafted layout/components in Cursor; I rewrote claims to stay honest about prototype status.

5. What I’d show in an interview

  1. Open the live demo and narrate a failure + recovery.
  2. Walk the three research questions and how I’d instrument them.
  3. Connect to hardware HF: waiting on sensors / tracking quality is a real constraint, like waiting on prototypes.
